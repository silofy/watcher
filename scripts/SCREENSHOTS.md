# Regenerating docs/screenshots/*.png

This is the tooling that captures `docs/screenshots/*.png` against the current lesson-first debrief —
a rich demo report, driven through a real Chromium via Playwright. Re-run it whenever the UI changes
so the README images stay current.

## One-time setup

```sh
npm install
npx playwright install chromium
```

## Run

```sh
npm run screenshots
```

This chains three steps (each also runnable on its own):

1. **`npm run gen:demo`** — runs `scripts/gen-demo-report.tsx` (vite-node), which replays the
   scripted "Forge" playthrough (`src/lib/demo/playthrough.ts`, the same data behind the
   `?demo=live` walkthrough) through `assembleReport` and writes the fully-graded output to
   `fixtures/session-demo-full.json`. Unlike the bundled default fixture
   (`fixtures/session-htb-easy.json`, schema v1.0), this one is schema v1.4 and carries ghost items,
   findings, and methodology/focus metrics — everything worth screenshotting. It's schema-validated
   by `tests/schema.test.ts` (which validates every `fixtures/session-*.json`), so it's committed to
   the repo like any other fixture.
2. **`npm run export -- --report fixtures/session-demo-full.json`** — builds `dist/` and renders
   that fixture into a self-contained `dist/report-from-capture.html` (no external JS/CSS/font
   requests; everything the export needs is inlined into the one file).
3. **`node scripts/screenshots.mjs`** — launches headless Chromium, opens that file over `file://`,
   and captures each debrief surface by its `data-shot="…"` anchor (see below), writing straight into
   `docs/screenshots/`.

`node scripts/screenshots.mjs` can also be run on its own — it re-runs steps 1 and 2 itself via
`child_process` first, so it's self-sufficient even outside the `screenshots` npm script.

## What this does NOT cover

**`docs/screenshots/live-ops.gif` is not regenerated by this script.** It's an animated capture of
the live `?demo=live` stream (the run building in real time), which needs frame-by-frame capture and
GIF encoding — a different pipeline from the single-shot PNGs above. Don't mistake a
`npm run screenshots` pass as having refreshed it.

It was last refreshed by hand (2026-09-23, editorial-dark redesign): with `npm run dev` running,
Playwright opened `/?demo=live` at a 1180×760 viewport (DPR 1) with `watcher.onboarded=1` preset in
localStorage and the `[data-demo-pill]` hidden, then screenshotted `#summary` (the Live Ops panel)
once per demo tick (2 s, `DEMO_TICK_MS`) until the run resolved: 26 frames. Pillow encoded them at
220 ms per frame (1.8 s hold on the last), one adaptive 256-colour palette per frame with dithering
off so the UI's Bayer dot patterns stay crisp, and shorter early frames padded at the bottom with the
page background to the final panel height.

## Note: an export bug this uncovered (fixed)

Running this end-to-end surfaced a pre-existing bug in the export path, unrelated to the
screenshot-tooling itself: `vite build` was splitting a small shared chunk (code behind a few
`import()`-lazy modules, e.g. `src/lib/llm/*`) into its own `assets/core-*.js` file alongside the
main `assets/index-*.js`. `scripts/export-html.tsx`'s `readAsset(".js")` only ever inlines the first
`.js` file it finds, so it was silently inlining the wrong (tiny, vendor) chunk — the exported
`report.html`/`report-from-capture.html` rendered fine (server-markup) but was completely
non-interactive (no tab switching, no drawer state, nothing JS-driven) with no visible error. Fixed
in `vite.config.ts` by forcing a single output chunk (`build.rollupOptions.output.inlineDynamicImports:
true`), so there's always exactly one JS asset to inline.
